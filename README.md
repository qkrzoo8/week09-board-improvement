## 📂 파일 구성 및 엔지니어링 특징

### 1. `server.js` (Express 백엔드 API)
- **대량 데이터셋**: 1,000건의 인메모리 게시글 데이터 자동 시드.
- **방어적 파라미터 파싱**: `parseInt(..., 10)` 기수 명시, 음수 및 0 페이지 차단, `Math.min(..., 100)` 대량 조회 공격 방어.
- **ORDER BY 화이트리스트 보안**: `SORT_WHITELIST` 객체 매핑으로 SQL Injection 원천 봉쇄 및 `id DESC` 동점자 방지 2차 정렬 결합.
- **2대 페이징 API 제공**:
  - `GET /api/posts`: 오프셋 기반 페이징 (`LIMIT` / `OFFSET`, 표준 `meta` Envelope 응답)
  - `GET /api/posts/cursor`: 고성능 커서 기반 페이징 (`WHERE id < ? ORDER BY id DESC LIMIT 10`, `limit + 1` 패턴으로 `COUNT(*)` 제거)

### 2. `index.html` (SPA 프론트엔드 & 실시간 DevTools 검사기)
- **탭 모드 전환**: [오프셋 번호 페이징] ↔ [커서 기반 무한 스크롤] 즉시 비교.
- **실시간 디바운스 (300ms)**: 연속 타이핑 시 불필요한 API 요청 폭격 방지.
- **AbortController 비동기 방어**: 새 검색어 입력 시 이전 진행 중인 fetch 요청을 즉각 취소하여 Race Condition 버그 예방.
- **브라우저 히스토리 동기화**: `URLSearchParams`와 `history.pushState` 및 `window.onpopstate` 이벤트로 뒤로 가기 / 새로고침 상태 복원 지원.

### 3. 주요 개념 설명

#### 3.1 오프셋과 커서 페이지네이션

오프셋 페이지네이션은 페이지 번호를 직접 선택하는 게시판, 검색 결과 화면 등에 적합하다. 전체 게시글 수와 페이지 수를 제공할 수 있다.

커서 페이지네이션은 마지막으로 조회한 게시글 ID를 기준으로 다음 데이터를 가져온다. 따라서 더 보기 버튼이나 무한 스크롤 방식에 적합하다.

본 실습의 커서 정렬 기준은 ID 내림차순으로 고정하였다.

#### 3.2 디바운스와 AbortController

디바운스는 사용자가 연속으로 입력하는 동안 API 요청을 지연시키고 마지막 입력 후 300ms가 지나면 검색 요청을 전송한다.

AbortController는 새로운 요청이 발생할 때 이전에 진행 중인 요청을 취소한다. 또한 요청 번호를 비교하여 오래된 응답이 최신 검색 결과를 덮어쓰지 않도록 방지하였다.

#### 3.3 limit + 1 원리

커서 페이지네이션에서는 요청한 limit보다 1개 더 많은 데이터를 조회하여 다음 페이지 존재 여부를 판단한다.

예를 들어 limit=10인 경우 최대 11개를 조회한다.

- 11개 조회: hasNext=true, 실제 반환은 10개
- 10개 이하 조회: hasNext=false

이를 통해 전체 게시글 수를 별도로 계산하지 않고 다음 페이지 존재 여부를 판단할 수 있다.

#### 3.4 offset과 totalPages 계산식

offset = (page - 1) × limit

totalPages = max(1, ceil(totalCount / limit))

예를 들어 전체 게시글이 1,000개이고 limit=10, page=3이면:

- offset = (3 - 1) × 10 = 20
- totalPages = ceil(1000 / 10) = 100

따라서 앞의 게시글 20개를 건너뛰고 21번째부터 조회한다.
